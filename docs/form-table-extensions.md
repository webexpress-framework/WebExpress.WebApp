# Form and table extension contracts

The form field API preserves update intent. `TryRead<T>(name)` reads a submitted value and `Detach<T>(name)` removes it before ordinary binding. Both return `RestApiFormField<T>` with `Missing`, `Empty`, `Valid`, or `Invalid`. Field names use ordinal case insensitive matching throughout `RestApiCrudFormData`, including binding. Null and whitespace denote an explicit empty value. JSON arrays are deserialized into the requested collection type without splitting their elements on semicolons. Incompatible array members or scalar targets return `Invalid`. Conversion errors carry a field-specific explanation. `ReadOptionalGuid(name)` also treats `Guid.Empty` as explicit removal. Applications must reject invalid fields before saving records.

The avatar API validates inline submissions. `DetachAvatar(name, options, validation)` accepts `file:<name>;data:<media-type>;base64,<payload>` and bare base64 data URLs. The filename never determines a storage path. `RestApiAvatarUploadOptions` configures the decoded byte limit and the media type to extension allowlist. PNG, JPEG, GIF and WebP are allowed by default with a four MiB limit. The media type is the declared data URL type; applications requiring full image decoding or image sanitization must perform that in their storage implementation. Invalid base64, unsupported types, empty payloads and exceeded limits produce field errors in `RestApiValidationResult`. Missing fields preserve existing images and explicitly empty fields request removal.

The avatar resolution API delegates application policy. `ResolveAvatar` accepts separate storage, public image resolution, removal and fallback callbacks. It invokes no callback for missing fields and refuses invalid fields. Applications call it only after validating the complete form, and own storage transactions, replacement cleanup, public addresses and fallback generation.

The table control exposes `EmptyText` as a render-context factory. Its result is localized and transferred to the browser as text. Successful empty results show this message, loading shows progress, and failed requests show an alert. Column management remains available in the header even when no rows or row actions exist.

The table layout API leaves persistence to the application. `TableCtrl.serializeLayout()` returns `{version:1,columns:[{id,visible,width}]}` and `applyLayout(value)` applies a stored snapshot. The server offers the corresponding `RestApiTableLayout.Capture`, `ToJson`, `Parse` and `Apply` methods. Order follows stable column identifiers, new columns are appended and removed columns are ignored. Server application returns fresh column definitions. Width is measured in pixels and null means automatic width. Omitted or null visibility preserves the current column visibility in both server and client layout application. Neither public layout application method writes application storage. Existing table configuration events and REST configuration hooks remain available.

The row contract supports hierarchy directly. Set `RestApiTableRow.Children` and `Expanded` to provide nested rows, and supply `RestApiTableCell.Content` as ordinary text by default. Prefer existing column templates for dates, editor content, status, links and other formatted content. The explicit `Html` cell property is reserved for trusted application markup. Cell template and link overrides are modeled as `Type`, `Uri`, `Icon`, `Image` and `Target`, so response rewriting is unnecessary.

The inline edit template configures a general editing workflow. `RestApiTableColumnTemplateInlineEdit` provides `Endpoint`, `Field`, `Kind`, `Editor`, `Method` and `Options`. The endpoint falls back to the row's REST address, the field to the column name, and the default HTTP method is PATCH. The row identifier is sent as the `id` query parameter, configurable through `idParameter`. Editors support text, textarea, select, number and date; `items` supplies select entries with `value` and `text`. Additional options include placeholder, min, max, step and maxLength. Display uses the existing template named by `Kind`.

The inline submission uses the service layer with an exact JSON body containing the configured field. Failed requests preserve the entered value and show returned field errors. Successful requests update the visible value and reload the owning table or ViewState resource. Applications supply endpoint behavior, choices, field mappings and server-side authorization. Hiding an editor never grants or revokes permission.
